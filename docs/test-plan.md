# 시험 계획서 — SpaceLink (CCSDS TM 다운링크 수신 처리)

> IEEE 829 의 시험 계획 항목을 이 프로젝트 규모에 맞게 줄였다. 결과는 [`test-report.md`](test-report.md), 요구사항은 [`requirements.md`](requirements.md).

## 1. 시험 대상

| 항목 | 내용 |
|---|---|
| SW | `SpaceLink` — Crc16Ccitt · TransferFrame/FrameConfig · SpacePacket/PacketHeader · FramePacker · PacketExtractor · ChannelCoding(GaloisField256 · ReedSolomonCodec · Pseudorandomizer · FrameSynchronizer · ChannelCodec) |
| 제외 | `benchmarks/` (성능 측정용, 배포물이 아니다) |
| 기준 문서 | `docs/requirements.md` — 기능 요구사항 REQ-* 25개 · 품질 요구사항 QR-01~04 |
| 기준 표준 | CCSDS 132.0-B (TM 전송 프레임) · 133.0-B (Space Packet) · 131.0-B 계열 (채널 부호·동기) |

## 2. 시험 목표

1. **핵심 계약을 지킨다** — 손상됐을 가능성이 있는 패킷은 절대 내보내지 않고, 손상과 무관한 패킷은 모두 복구한다. 뒷단이 수신기를 믿고 처리하므로 **조용한 손상은 유실보다 나쁘다.**
2. 모든 기능 요구사항이 최소 1개의 **통과한** 시험으로 검증된다 (`tools/trace.py` 가 자동 검사).
3. 기대값은 구현과 **독립된 근거**에서 온다 — 구현 결과를 복사해 기대값으로 쓰지 않는다.
4. 구조 커버리지뿐 아니라 **결함 검출력**(뮤테이션 점수)을 측정하고, 생존 변이를 **전부 판정**한다.
5. 성능은 **측정 방법을 먼저 세운 뒤** 잰다 (§7 의 오염 사례).

## 3. 시험 기법과 기대값의 출처

| 기법 | 기대값의 출처 | 적용 대상 |
|---|---|---|
| 표준 검사값 | 규격 문서 ("123456789" → 0x29B1) | CRC-01 |
| 독립 구현 대조 | 표 기반 CRC ↔ 비트 단위 기준 구현 (무작위 3,000 버퍼) | CRC-01 |
| 수작업 비트 벡터 | 규격의 비트 배치를 손으로 계산 | FRM-01 · PKT-01 |
| 전수 | 입력 공간 전부 (1,115 바이트 프레임의 단일 비트 오류 8,920 가지) | FRM-02 |
| 왕복 | 부호화 ↔ 복호화 (무작위 프레임 4,000 · 패킷 5,000) | FRM-01 · PKT-01 · RS-01 |
| 결함 주입 | 채널 이상 모형 — 유실 2·5·20 % · 비트 오류 · 중복 · 순서 뒤바뀜 | EXT-03 · EXT-04 |
| 모형 대조 | 송신 모델이 기록한 패킷·프레임 구간 (`Downlink.Link.Overlaps`) 으로 **기대 생존 집합**을 계산 | EXT-03 |
| 구성된 입력 | 무작위로는 사실상 안 나오는 모양을 체 이론으로 직접 만든다 (S17 만 남기기, S1…S30 지우기) | RS-03 |
| 강건성 | 무작위 바이트 50,000 · CRC 가 맞는 무작위 프레임 50,000 | EXT-07 |
| 뮤테이션 | Stryker.NET 으로 코드를 일부러 망가뜨려 시험이 잡는지 | 전체 |
| 벤치마크 | BenchmarkDotNet 단일 스레드 + MemoryDiagnoser | EXT-08 |

## 5. 합격 기준 (빌드·CI 게이트)

| # | 기준 | 어디서 막나 |
|---|---|---|
| QR-01 | 컴파일러·.NET 분석기 경고 0 | `TreatWarningsAsErrors` (빌드) |
| QR-02 | 라인 ≥ 90 % · 분기 ≥ 85 % | coverlet `/p:Threshold` (시험 단계) |
| QR-03 | 뮤테이션 ≥ 80 % | Stryker `--break-at 80` (mutation 잡) |
| QR-04 | ubuntu·windows 동일 결과 | CI 매트릭스 |
| — | 요구사항 추적 누락·실패 0 | `tools/trace.py` 종료 코드 (시험 단계) |
| REQ-EXT-08 | 프레임당 할당 ≤ **벤치마크별 예산** (추출 260 B · 채널 체인 870 B · 심볼 오류 정정 경로 2,150 B) | benchmark 잡 — `tools/check_allocation.py` (예산 표에 없거나 결과에 없는 벤치마크도 실패) |

**성능 게이트를 시간이 아니라 할당으로 거는 이유** — 공유 러너는 실행 시간이 크게 흔들려 시간 기준은 거짓 실패를 만든다.
프레임당 할당량은 러너 성능과 무관하고, 지금 개선(443 → 244 B)이 되돌아가는 것을 정확히 잡는다.

## 6. 결함 관리

- 결함을 찾으면 **먼저 그 조건에서 재현되는 시험**을 고정하고(RED), 고친 뒤 통과(GREEN)를 확인한다.
- 제품 결함과 시험 결함을 구분해 보고서에 적는다 — 지금까지 제품 결함 C-1(감지되지 않는 유실에서 손상 패킷), 직접 쓴 채널 부호 코드에서 CH-1~CH-3.
- **생존한 변이는 전부 판정한다** — 메시지 문자열 / 관찰상 동등 / 성능 정책 / 실제 시험 약점. 약점은 숨기지 않고 남은 채로 적는다.
- 도달할 수 없는 가지는 시험으로 덮지 않고 **삭제한다** (커버리지·뮤테이션이 영영 채워지지 않는다).

## 7. 위험과 한계

| 위험 | 지금 상태 |
|---|---|
| 측정 방법이 숫자를 만든다 | 실제로 겪었다 — 처리량을 시험 안에서 재다 병렬 부하가 섞여 20~25 배 낮게 나왔다 (§8). 성능은 전용 벤치마크에서만 잰다 |
| ~~규격 미구현으로 실제 비트열과 비호환~~ → 근·이중 기저를 표준대로 고쳤다 | RS 생성 다항식의 근(`β^112…β^143`, β=α^11)과 이중 기저(dual basis) 변환을 CCSDS 131.0-B-5 부속서 F·G 와 값으로 대조했다(2026-09-22). 남는 것은 비트 전송 순서(§4.3.9.2)뿐 — 실제 캡처와 대조하지 못했다 |
| ~~표준 문서 미보유~~ → 표준을 받아 대조했다 | PN 수열은 표준(CCSDS 131.0-B-5 §10.4.3)의 처음 40 비트와 **값으로** 대조한다 — 그러자 구현이 틀려 있었다(CH-4). **RS 는 아직 표준의 코드가 아니다**(생성 다항식의 근 · 이중 기저 변환). 표준 PDF 는 저장소 밖에 둔다 |
| 관측되지 않은 것을 증명으로 읽기 | 오정정이 3,000 회 중 0 건이라, "오정정은 CRC 가 걸러낸다" 는 **확인된 것이 아니다.** 관측되면 잡도록 단언만 걸어 뒀다 |
| 시험이 구현에 과적합 | 메시지 문구·구현 세부(할당 횟수·버퍼 증가 **정책**)는 단언하지 않는다. 그래서 죽지 않는 변이가 남는 것을 받아들인다. 다만 **유계성은 계약이다**(REQ-ASM-04) — 증가 정책이 아니라 상한만 단언한다 |
| 범위 밖 | 컨볼루션·터보·LDPC 부호, AOS 프레임, 패킷 부헤더(시각 코드) |
