## 2. 제품 결함 C-1 — 감지되지 않는 유실에서 손상 패킷 출력

| 항목 | 내용 |
|---|---|
| 증상 | 256 장 단위로 프레임이 연속 유실되면 조립 중이던 패킷에 다른 패킷의 뒷부분이 이어 붙어, 원본에 없는 패킷이 나갔다 (시험 5건 실패) |
| 원인 | 8 비트 가상 채널 프레임 카운트가 한 바퀴 돌아 유실이 보이지 않는다. 프레임 CRC·카운트·제1 헤더 포인터는 모두 프레임 단위 정보라, 경계가 우연히 맞으면 프레임 계층만으로는 잘못 이어 붙인 패킷을 **원리적으로** 구분할 수 없다 |
| 영향 | 뒷단(영상·텔레메트리 처리)이 수신기를 믿고 처리하므로, 조용한 손상은 유실보다 나쁘다 |
| 조치 | 패킷 오류 제어(PEC, 패킷 끝 CRC-16)를 선택 기능으로 추가. 불일치하면 버리고 다음 제1 헤더 포인터에서 재동기. 비용은 패킷당 2 바이트 |
| 확인 | PEC 없이 손상 패킷이 실제로 나오는 것을 고정한 시험 1건 + PEC 켠 상태에서 256·512 장 연속 유실 × 40 시도 × 5 시드 손상 0 + 패킷 단일 비트 오류 전수 검출 (REQ-EXT-06) |

## 4. 뮤테이션 분석 — 생존 18개를 전부 판정한다

생존 18개를 하나씩 보고 **세 부류**로 나눴다.

| 부류 | 개수 | 판정 |
|---|---|---|
| 사람이 읽는 메시지 문자열 | 10 | 이벤트 `Detail` · 예외 메시지를 `$""` 로 바꾼 변이. 관찰 가능한 동작(이벤트 종류·예외 형)이 그대로라 시험이 잡지 않는다. 메시지 문구는 계약이 아니므로 **시험 대상에서 제외**한다 |

### 4.1 드러난 시험 약점과 보강

| 생존 변이 | 무엇이 안 잡혔나 | 보강한 시험 |
|---|---|---|
| `FrameConfig` 경계 비교 `<` → `<=`, `>` → `>=` (2건) | 데이터 필드 길이의 **거부 쪽**(6 바이트·2047 바이트)만 시험해서, 경계값 7·2046 을 잘못 거부하게 만들어도 통과했다 | `TransferFrameTests#Data_field_length_limits_are_inclusive_at_both_ends` — 경계 두 값이 받아들여지는지 확인 |
| 유실 개수 `(count - expected + 256) % 256` 변형 (3건) | `FrameGap` 이벤트가 **나오는지**만 보고 `lost=` 값을 보지 않았다 | `FaultInjectionTests#Frame_gap_event_reports_how_many_frames_were_lost` — 프레임 3장을 빼고 `expected=5 got=8 lost=3` 을 확인 |
| 잘못된 패킷 버전에서 `channel.Desynchronize()` 삭제 (1건) | 동기를 풀지 않아도 같은 프레임 안에서는 차이가 없어 안 잡혔다. **뒤따르는 프레임**에서 같은 쓰레기 버퍼가 다시 읽힌다 | `FaultInjectionTests#Invalid_packet_version_desynchronizes_until_the_next_first_header_pointer` — 프레임 3장(잘못된 헤더 → 연속 데이터 → 정상 패킷)으로 이벤트 1건·출력 1개 확인 |

### 4.2 명세 공백

마지막 변이는 **요구사항이 없는 동작**을 가리켰다. "패킷 버전 번호가 0 이 아니면 동기를 잃은 것으로 보고 다음 제1 헤더 포인터까지 버린다" 는 코드와 이벤트 열거형에는 있었지만 요구사항 표에는 없었다.
**REQ-EXT-09** 로 명세에 올리고 시험을 연결했다.

| | 기준선 | 보강 후 |
|---|---|---|
| 점수 | 93.24 % | **96.28 %** |
| 죽임 · 타임아웃 | 232 · 44 | 225 · 60 |
| 생존 | 18 | **11** |
| 미커버 | 2 | **0** |

죽은 변이 7개는 §4.1 의 약점 6건과 `FrameGap` 메시지 하나다 — `lost=` 값을 확인하는 시험이 그 문자열까지 같이 잡았다.
채점 대상은 296개로 같고, 타임아웃이 44 → 60 으로 는 것은 시험이 늘어 무한 루프로 빠지는 변이가 더 걸린 것이다 (타임아웃은 죽은 것으로 센다).

**남은 11개는 전부 §4 의 앞 두 부류다** — 메시지 문자열 9, 관찰상 동등 2. 메시지 문구를 계약으로 삼지 않는 한 이 점수가 상한이다.

### 4.4 처리량 재작성 뒤 재측정 — 95.12 % (생존 16)

§8 의 재작성으로 코드가 바뀌었으니 다시 쟀다 ([run 35067912044](https://github.com/Haejyn/ccsds-downlink-reliability/actions/runs/35067912044), 세 잡 성공 · 커버리지 100 % 유지).

| | 시험 보강 직후 | 처리량 재작성 뒤 |
|---|---|---|
| 점수 | 96.28 % | **95.12 %** |
| 죽임 · 타임아웃 | 225 · 60 | 242 · 70 |
| 생존 | 11 | **16** |
| 채점 대상 | 296 | **328** |

**점수가 내려갔지만 시험이 약해진 것은 아니다.** 새 코드(검증 뷰·지연 할당·오프셋 버퍼)로 채점 대상이 32 개 늘었고, 죽인 변이도 225 → 242 로 늘었다.
새로 생존한 5 개를 하나씩 보면 **기능을 바꾸는 것은 하나도 없다.**

| 새 생존 | 판정 |
|---|---|
| `Drain` 의 `return;` 삭제 | **관찰상 동등** — 바로 위 `Desynchronize()` 가 `InSync` 를 false 로 만들어 `while (channel.InSync …)` 가 어차피 곧바로 끝난다 |
| `EnsureRoom` 의 증가량 `Math.Max(_buffer.Length * 2, pending + length)` 변형 3 개 (`Min` · `/2` · `pending - length`) | **기능상 동등, 성능 정책만 다름** — 어느 쪽으로 바뀌어도 필요한 크기는 항상 확보된다. 잡으려면 할당 횟수를 단언해야 하는데, 그건 구현 세부를 시험에 박는 일이라 하지 않는다 |
| `InvalidPacketHeader` 의 `$"version={header.Version}"` | **메시지 문자열** — 예전에는 미커버(채점 제외)였고, 새로 넣은 동기 해제 시험이 그 줄을 지나면서 "커버되지만 검증하지 않는" 상태로 드러났다 |

생존 16 개 전체는 **메시지 문자열 10 · 관찰상 동등 3 · 성능 정책 3** 이다. §4 의 원칙(문구는 계약이 아니다)을 유지하는 한 이 근처가 상한이다.

## 5. 커버리지 미도달 지점 — 라인·분기 모두 100 % 로

기준선의 미커버 2줄은 모두 `SpacePacket` 에 있었다 — 데이터가 3 바이트 미만이라 PEC 를 담을 수 없을 때의 조기 반환과, 값 동등성 보조 메서드다.
둘 다 시험을 더해 덮었다 (`Error_control_check_is_false_when_the_packet_cannot_hold_a_crc`, `Value_equality_distinguishes_packets_by_content`).

남아 있던 분기 1개(132 중 1)는 `FrameConfig.DataFieldLength` 의 **FECF 를 끈 형식**이었다. 지원하는 설정인데 시험이 하나도 없었고,
그 경로는 `Decode` 가 **CRC 검사를 건너뛴다**. `Frames_without_frame_error_control_round_trip` 으로 왕복을 확인하고,
FECF 가 없으면 마지막 바이트를 바꿔도 프레임이 유효하다는 것(오류가 걸러지지 않는다)까지 고정했다. 이로써 라인 305/305 · 분기 132/132 다.

## 6. 요구사항 추적

`python tools/trace.py` 가 `docs/requirements.md` 의 REQ 행, 시험 코드의 `[Trait("Requirement", …)]`, `dotnet test` 가 남긴 TRX 결과를 대조해 [`traceability.md`](traceability.md) 를 만든다.
명세에 있는데 시험이 없거나, 시험이 가리키는 ID 가 명세에 없거나, 연결된 시험에 실패가 있으면 종료 코드 1 이다.

품질 요구사항(QR-01~04)은 시험이 아니라 **빌드·CI 게이트**로 지킨다 — 경고를 오류로 취급, coverlet 임계값, Stryker `--break-at 80`, ubuntu·windows 매트릭스.

## 7. 한계와 다음

- 리드-솔로몬·ASM 동기 탐색·PN 랜덤화는 **§9 에서 범위 안으로 들어왔다**. RS 의 생성 다항식 근과 이중 기저 변환은 **§9.7 에서 표준대로 고쳤다**(부속서 F·G 와 값 대조). 짧은 프레임의 가상 채움(§4.3.7)은 **§9.8 에서 넣었다**. 공개 구현 libfec 와 바이트 단위로 같다(§9.10). **실제 위성 캡처도 프레임 CRC 까지 복호한다(§9.11)**
- 컨볼루션·터보·LDPC 부호, AOS 프레임, 패킷 부헤더(시각 코드)는 범위 밖이다
- 메시지 문자열은 계약이 아니라고 판단해 시험하지 않는다. 운용에서 메시지를 파싱해 쓰기 시작하면 그때 계약으로 올려야 한다

### 8.5 체인 전체 처리량 — 2.85 Gbps 는 추출 단계의 숫자였다 (2026-09-21)

**읽는 법**
- **체인은 추출 단계의 약 1/95 다** (같은 실행의 390.4 ns 대 37,067 ns). 시간의 **99 % 가 ASM 동기·PN·RS 복호에 들고 추출은 1.05 %** 다. "수신기가 2.85 Gbps" 라고 읽히던 숫자는 체인의 마지막 1 % 의 속도였다.
- **오류가 없어도 RS 비용은 그대로 든다.** `ReedSolomon.cs:174` 는 신드롬이 전부 0 이면 곧바로 반환하지만 그 신드롬 32 개를 구하는 데 부호어당 GF 곱 8,160 번(255 × 32)이 든다. 정정이 실제로 돌면(Berlekamp-Massey · Chien · Forney) 거기에 **+26 %**, 할당은 **약 2 배**(1,247 → 2,443 B)다.
  시간을 단계별로 쪼개지는 않았다 — 신드롬 계산이 대부분일 것으로 **추정**하지만 프로파일링으로 확인하지 않았다. 정정 경로의 할당 증가 원인도 같다(Berlekamp-Massey 의 배열 복제로 **추정**).
- **2 Gbps 채널율**을 받으려면 초당 2×10⁹ ÷ (259 B × 8) = **965,251 CADU** 가 필요하다. 이 체인은 **그 2.8 %(약 1/36)** 다 — 단일 스레드 기준이며 병렬화는 시험하지 않았다.
- **REQ-EXT-08 은 이 체인에 대해서는 미달이다.** 요구값 1,000,000 프레임/초는 추출 단계에 대한 것이었다. 문구가 모호했던 것을 요구사항에서 분명히 했다.

**측정 조건 — 시간 값은 흔들린다.** 측정이 끝난 직후 이 작업의 프로세스가 없는 상태에서 `Get-Counter` 로 CPU 를 8 초 재니 **30~60 %** 였다(다른 프로그램의 배경 부하). 측정 도중의 부하는 직접 재지 못했다.
추출 단계가 §8.4 의 기록(359 ns)보다 8.7 % 느리게 나온 것이 그 흔적이다. 그래서 **절대 시간은 조용한 기계에서 다시 재야 한다.**
반면 **할당(바이트)은 부하와 무관**하고, 체인 대 추출의 **비율 95 배**는 수십 % 의 잡음으로 뒤집히지 않는다. 결론은 이 둘에서만 끌어냈다.

## 9. 채널 부호·프레임 동기 — 검출에서 정정으로 (2026-09-16)

지금까지 이 저장소는 오류를 **검출**만 했다(CRC). 지상국 수신 체인에서 그보다 앞단인 **정정** 계층을 넣고, 정정 능력을 실측으로 고정했다.

```
보낼 때:  프레임 → RS(255,223) 부호화 → PN 랜덤화 → ASM 붙임 → CADU
받을 때:  ASM 탐색(비트 단위) → PN 되돌림 → RS 복호 → 프레임
```

⚠ 처음 넣었을 때는 **CCSDS 의 코드가 아니었다** — 체 생성 다항식(0x187)과 정정 능력(t = 16)만 표준과 같고, 생성 다항식의 근은 `α^1 … α^32`
(표준은 `(α^11)^j, j = 112 … 143`), 이중 기저(dual basis) 변환도 없었다. **2026-09-22 에 둘 다 고쳤다(§9.7)** — 지금은 부속서 G 의
생성 다항식 계수표·부속서 F 의 변환 행렬과 값으로 대조한 표준의 코드다. 비트 전송 순서(§4.3.9.2)는 실제 위성 캡처로 확인했다(§9.11).
PN 수열은 2026-09-21 에 표준 문서(CCSDS 131.0-B-5)를 받아 **처음 40 비트와 대조**했다 (§9.6).

### 9.1 RS 정정 능력 — 경계를 실행으로 고정한다

| 주입한 심볼 오류 t | 결과 |
|---|---|
| 0 … 16 (각 시드 5 개) | **전부 정정** — 정정한 심볼 수 = 주입한 수, 데이터가 원본과 일치 |
| 17 · 18 · 20 · 24 · 32 (각 600 회, 합 3,000) | **3,000 / 3,000 실패 선언**, 오정정 **0 건** |

- 인터리빙 깊이 I 에서 **연속 I·16 심볼 버스트**가 정정된다 (부호어마다 16 개씩 흩어지므로). 같은 버스트를 깊이 1 로 받으면 복원에 실패한다 — 인터리빙이 하는 일이 정확히 그것이다.
- **오정정이 한 번도 관측되지 않았다.** 그러므로 "오정정이 나도 CRC 가 걸러낸다" 는 **이 시험으로 확인된 것이 아니다.** 관측되면 잡도록 단언은 걸어 두었다 (프레임을 훼손한 오정정이 CRC 까지 통과하면 실패).
- 무작위 바이트 3,000 블록을 넣어도 예외 없이 실패로 보고한다 — 수신기의 REQ-EXT-07 과 같은 계약이다.

**9.5 후속 (2026-09-21) — 숙제 (2)(3) 을 닫으면서 판정 셋이 틀렸음을 알았다**

**(1) 버퍼 — "구현 세부라 단언하지 않는다" 가 틀렸다.** 메모리가 유계인가는 실시간 수신기의 계약이다. 입력에 비례해 버퍼가 자라는 수신기는 성능이 나쁜 게 아니라 **고장난 것**이다.
정확한 값이 아니라 **상한만** 계약으로 삼았다 — `FrameSynchronizer.BufferedBytes`(public)와 REQ-ASM-04: 스트림을 1,000 B 조각으로 넣는 동안(당시 1 MB, 지금 판정 기준은 CADU 4,000 장) CADU 두 장 이하, 탐색 중 5 B 이하.
그런데 상한 시험을 써도 뮤턴트가 죽지 않았다. **`Trim()` 이 세 곳(루프 안 · `TrySearch` 끝 · `Process` 끝)에서 불리는 중복이었기 때문이다.**
`TrySearch` 끝의 호출은 곧바로 `break` 해서 `Process` 끝의 호출이 같은 상태에서 다시 실행하고, 루프 안의 호출은 그 호출의 최대 점유를 줄이지 못하면서
코드블록마다 `RemoveRange` 로 남은 버퍼 전체를 앞으로 당겨 큰 입력에서 제곱 시간이 된다. 하나를 지워도 나머지가 덮어 주니 **어떤 시험도 죽일 수 없었다** —
시험이 약한 게 아니라 제품 코드가 중복이었다. 둘을 지우고 나서야 남은 하나가 하중을 받았고, 상한 시험이 그것을 죽인다.
같은 이유로 `dropBytes <= 0` 가드도 지웠다 (`keepFrom >= _consumedBits` 불변식으로 음수가 될 수 없고 0 바이트 `RemoveRange` 는 무연산이다).

**(2) `continue` 삭제 — "메모리·흐름에만 영향" 이 틀렸다.** 130 줄의 `continue` 를 지우면 방금 **버리기로 판정한 경계**의 코드블록이 한 장 더 나간다 —
"손상됐을 가능성이 있는 데이터는 내보내지 않는다" 는 핵심 계약 쪽이다. 기존 재동기 시험은 **복호에 성공한 장수**만 세서, 뭉갠 것이 마커뿐이라 온전한 코드블록이
새어 나가도 그 수는 그대로였다. 새 시험은 어느 프레임이 빠졌는지까지 고정한다(0~7 · 9~11, 8 번 제외).
허용치 `>` ↔ `>=` 도 같은 곳에서 죽는다 — 기존 시험은 손상 마커를 6 연속으로 넣고 `>=` 로만 단언해 경계의 바로 위·아래를 구분하지 못했다. 새 시험은 **정확히 허용치만큼(3)** 과 **하나 더(4)** 를 구분한다.

**(3) Ω·형식 미분 — 시험의 약점이 아니라 동등 뮤턴트와 죽은 조건이었다.** `BerlekampMassey` 는 Λ 를 언제나 33 칸으로 돌려주고 `ErrorEvaluator` 의 `i` 는 0…31 이라
`j < lambda.Length` 는 **항상 참**이었다. `FormalDerivative` 의 `Math.Max(1, len − 1)` 도 발동한 적이 없다 — §9.4 와 같은 원칙으로 시험 대신 지웠다.
`j <= i` → `j < i` 는 Ω 에 `S₀·Λ(x)` 를 더할 뿐인데 Ω 는 Λ 의 **근에서만** 평가되므로(Λ = 0) 결과가 같다 — **증명으로 동등**이다.
이것을 `internal` 로 열어 독립 계산으로 대조했다면 뮤턴트를 죽일 수는 있었겠지만, 계약이 아닌 "Ω 의 계수 표현" 을 계약으로 올리는 일이었다.

### 9.6 PN 수열 — 표준을 받아 값으로 대조했더니 틀려 있었다 (2026-09-21)

§9 도입부는 "표준 문서의 예시와 대조하지 못했다(문서 미보유)" 라고 적었다. CCSDS 블루북은 공개돼 있어 받았다
(131.0-B-5, [ccsds.org/Pubs/131x0b5.pdf](https://ccsds.org/Pubs/131x0b5.pdf)). §10.4.3 NOTE 2 가 255 비트 랜덤화기의 **처음 40 비트를 값으로** 싣는다.

```
1111 1111 0100 1000 0000 1110 1100 0000 1001 1010   =   FF 48 0E C0 9A
```

| | 처음 5 바이트 | 주기 |
|---|---|---|
| **표준** (§10.4.3 NOTE 2) | `FF 48 0E C0 9A` | 255 |
| 구현, 탭 `0xD4` (수정 전) | `FF 1A AF 66 52` | 255 |
| 독립 기준 (선형 점화식) | `FF 48 0E C0 9A` | 255 |
| 구현, 탭 `0x95` (수정 후) | `FF 48 0E C0 9A` | 255 |

**CH-4 · 구현의 PN 수열은 표준의 수열이 아니었다.** 탭 마스크가 `0xD4`(비트 7·6·4·2)였는데 맞는 값은 `0x95`(비트 0·2·4·7)다.
h(x) = x⁸+x⁷+x⁵+x³+1 은 점화식 s[n+8] = s[n+7]⊕s[n+5]⊕s[n+3]⊕s[n] 이고, 상태 바이트에서 s[n+k] 가 비트 7−k 에 있으므로
지수 7·5·3·0 은 비트 0·2·4·7 자리다. 8 비트 상태 모델에서 탭 마스크 255 개를 전수로 돌려 표준의 40 비트와 일치하는 것을 찾으면 **`0x95` 하나뿐**이다.

**왜 성질 시험이 못 잡았나.** 자기 역원 · 주기 255 · 첫 바이트 `0xFF` 는 **최대 길이 LFSR 이면 어느 다항식이든** 만족한다.
`0xD4` 는 다항식이 다를 뿐 최대 길이 LFSR 이라 세 시험 모두 통과했다. 게다가 이 상수는 한 번 "고쳐진" 적이 있다(CH-1) —
주기 217 이 나와서 탭을 바꿨고, **주기가 255 로 돌아오자 맞다고 믿었다.** 주기는 필요조건이지 충분조건이 아니다.
기댈 곳은 구현 밖의 값뿐이었고, 시험이 스스로 만든 기준(점화식)조차 **표준의 40 비트로 먼저 교차 확인**한 뒤에야 믿을 수 있었다.

**고친 것** — `Pseudorandomizer.FeedbackTaps` `0xD4 → 0x95`, 그리고 값으로 못 박는 시험 둘.
(1) `Sequence_starts_with_the_forty_bits_the_standard_prints` — 표준의 `FF 48 0E C0 9A`
(2) `Sequence_matches_an_independent_linear_recurrence_over_three_periods` — 시험 안에서 **다른 꼴**(전체 비트열 위의 점화식)로 쓴 기준과 765 바이트 전량 일치.
수정 전에 두 시험이 실제로 실패한 기록: `수열의 처음 40 비트가 표준의 FF 48 0E C0 9A 와 다르다 (실제 FF1AAF6652)`.

**영향** — 이 구현끼리는 왕복했으므로(자기 역원) 기존 시험은 전부 초록이었다. 그러나 **실제 CCSDS 송신기가 랜덤화한 스트림을 이 수신기는
풀지 못했고, 반대도 마찬가지였다.** 수정 뒤에도 남는 한계: 표준이 기본으로 정한 131071 비트 수열(x¹⁷+x¹⁴+1)은 구현하지 않았다 — 255 비트는 옛 시스템 호환용이다. → **§9.9 에서 했다.**

**같은 종류의 틀림이 RS 에도 있었다.** 이 표준을 처음으로 읽고서 알게 됐다 — 생성 다항식의 근이 표준(§4.3.4)은 `(α¹¹)^j, j = 112 … 143` 인데
구현은 `α¹ … α³²` 다. 이중 기저 변환이 없다는 것만 한계로 적어 왔지만 **코드 자체가 표준의 RS 코드가 아니었다.** → **§9.7 에서 고쳤다.**

### 9.7 RS 를 표준의 코드로 — 근을 고치고 이중 기저 변환을 넣는다 (2026-09-22)

표준을 다시 읽고 두 가지를 실제로 고쳤다. 문서만 고치는 대신 코드를 바꾸고, 표준 문서로 값을 직접 대조했다.

**1) 부호 생성 다항식의 근 — `α^1…α^32` → `β^112…β^143`(β = α^11).** 표준(§4.3.4)의 형태를 그대로 옮겼다.
**부속서 G 가 계수 32 개(G0…G32)를 지수로 싣는다** — 새 근으로 g(x) 를 계산해 이 표와 **32 개 전부 값으로 일치**함을 확인했다
(`StandardConformanceTests.Generator_polynomial_matches_the_exact_coefficients_ccsds_publishes`). 표를 그대로 옮기는 것으로 끝나지 않고,
Python 으로 근 공식만으로 g(x) 를 독립적으로 유도해 같은 결과를 얻은 뒤에야 C# 으로 옮겼다 — 문서 표를 베낀 게 아니라 **재현**했다.

**2) 이중 기저(dual basis) 변환 — 부속서 F.** 부호 계산(신드롬·BM·Chien·Forney)은 관례 기저로 하고, 전송 바이트만
`DualBasisTransform` 이 이중 기저로 바꾼다(§4.3.9). 정보 심볼은 전송 바이트 그대로 나가고(정변환·역변환이 항등이라 계산하지 않는다),
새로 만든 패리티만 변환한다. 8×8 GF(2) 행렬 두 개(T_λ·T_λ⁻¹)는 문서에 **§4.3.9.3 과 부속서 F 두 곳에 다른 표로 실려 있는데 바이트 단위로
일치했다** — 우연이 아니라 서로 대조가 되는 것으로 읽는다. 256 개 값 전부 왕복하는지, 문서가 값으로 싣는 예시 두 개(α^7·α^0)와 맞는지
시험으로 고정했다(`Dual_basis_transform_round_trips_for_every_byte_value`, `Dual_basis_of_known_field_elements_matches_the_standards_matrix`).

**PN 때와 같은 함정을 다시 만났다** — pdftotext 가 그리스 문자를 지워 §4.4.2 의 "β = α^117" 이 "= 117" 로만 남았고, 처음엔 "α^11" 로
잘못 읽어 궤도가 어긋난 채로 대조를 시도했다(orthogonality 검사가 실패로 나왔다). 페이지를 이미지로 렌더링해 직접 읽고서야 지수가 117 임을
확인했다 — 이 β 는 RS 근 간격 α^11 과 **별개**의, §4.4.2 가 이중 기저 개념을 설명하려고 든 예시 기저였다. 텍스트 추출을 그대로 믿지 않고
숫자가 걸린 자리는 이미지로 다시 확인하는 습관이 PN 사건(CH-4)에 이어 다시 값을 냈다.

**Forney 공식에 보정 인수가 필요했다.** 근이 β^0 이 아니라 β^112 부터 시작하므로(FCR = 112), 오류 크기 계산에 `X_k^(1−FCR)` 인수가
더 필요하다 — 표준 Forney 공식(FCR = 1)은 이 인수가 1 이 되어 사라지는 특수한 경우였다는 것을, 유도를 끝까지 해보고서야 알았다.
유도는 Python 으로 신드롬 정의부터 다시 밟아 b=1(기존 구현) 특수해와 일치하는지 먼저 확인한 뒤, t=16 경계까지 무작위 300 회(오류
없음·정확히 t=16 개·이중 기저 도메인에서 XOR 주입)를 시뮬레이션해 전부 통과함을 본 뒤에야 C# 으로 옮겼다.

**옮기며 걸린 시험 하나** — `ReedSolomonFailurePathTests.cs` 의 "30 개 신드롬을 지우는" 시험은 근을 `α^1…α^30` 으로 직접 계산해
생성 다항식과 대조하던 것이라, 근이 바뀌자 그 계산도 `β^112…β^141` 로 다시 써야 했다. 고치는 과정에서 두 번째로 걸린 것 —
`Encode` 가 정보 심볼을 이제 이중 기저로 받으므로, 시험이 "관례 기저 값 1" 을 넣으려면 `DualBasisTransform.ToDualBasis(1)` 을 미리
걸어야 했다(그냥 `1` 을 넣으면 내부에서 `0xCC` 로 바뀐다). 첫 실패(`Expected: 123, Actual: 1`)가 바로 이 지점을 가리켰다.

**검증** — 기존 시험 97 개 중 96 개는 **손대지 않고 그대로 통과했다**(라운드트립·정정 개수·버스트·경계값은 근·기저에 무관한 성질이다).
고친 것은 위 두 지점(생성 다항식 대조·주입 좌표)뿐이었고, 뮤턴트를 직접 심어(근 간격을 11→7로) 새 시험이 잡는 것도 확인했다.
전체 102 통과·경고 0·커버리지 100 %·추적 24/24. **뮤테이션은 이번에 다시 재지 않았다** — RS 알고리즘 구조 자체는 안 바뀌어서(같은

### 9.8 짧은 코드블록 — 가상 채움을 앞에 두고 보내지 않는다 (2026-09-23)

§9.7 에서 "RS 는 이제 표준의 코드" 라고 적었지만 **223 바이트 프레임에서만 맞았다.** 이 저장소의 프레임은 전부 128 바이트다.

**CH-5 · 짧은 프레임을 표준과 다르게 보냈다.** 표준(§4.3.7)은 프레임이 223·I 보다 짧으면 코드블록 **앞쪽** Q 심볼을 0("가상 채움")으로 쳐서
체크 심볼을 계산하고, 그 Q 개는 **부호기에 넣지도 보내지도 않는다**(§4.3.7.4). 이 구현은 프레임을 앞에 두고 **뒤를** 0 으로 채워 255 바이트를 **전부** 보냈다.
- 128 바이트 프레임의 CADU 가 **259 바이트**였다. 표준대로면 ASM 4 + 프레임 128 + 체크 32 = **164 바이트** — 보내던 바이트의 37 % 가 0 이었다.
- 채움 자리가 달라 **패리티도 표준 부호기와 달랐다**(0 이 다항식의 높은 차수가 아니라 중간에 놓였다). 실제 CCSDS 수신기는 이 코드블록을 복호하지 못한다.
- 기존 시험이 못 잡은 이유: 자기 부호기와 자기 복호기가 같은 방식으로 틀렸으니 왕복은 늘 맞았다. PN(CH-4)과 같은 모양이다 — **외부 정의와 대조하지 않으면 드러나지 않는다.**

**고친 것** — `ReedSolomonCodec(interleavingDepth, virtualFill)`. Q 는 I 의 배수이고 kI 보다 작다(§4.3.7.3). 레인마다 앞쪽 Q/I 심볼을 0 으로 두고 부호화하고,
전송 코드블록에서는 그 자리를 빼 앞으로 당긴다. `ChannelCodec` 은 프레임 길이로 Q 를 계산한다 — 그래서 **프레임 길이가 I 의 배수가 아니면 거부**한다.

**복호기의 새 규칙 — 채움 자리로 정정하면 실패.** 채움 자리는 0 인 게 확실하다. Chien 탐색을 보낸 자리에서만 하므로, 근이 채움 자리에 있으면
찾은 근의 수가 모자라 실패로 빠진다. 이 규칙이 없으면 무슨 일이 생기는지 시험으로 직접 만들었다 — 채움 자리와 거리 1 인 부호어로 가는 수신어를
구성하면(최소 거리 33 이라 16 안쪽의 부호어는 그것 하나뿐이다), 규칙을 지운 복호기는 **첫 바이트가 `B4` → `77` 로 바뀐 프레임을 "성공" 으로 내보냈다.**
이 저장소의 핵심 계약("손상됐을 가능성이 있는 패킷은 내보내지 않는다")에 바로 걸리는 자리다.

**기대값의 출처** — 표준의 정의 그대로다: 짧은 코드블록 = 앞에 0 을 Q 개 붙여 **전체 길이**로 부호화한 부호어에서 그 Q 개를 뗀 것. 전체 길이 부호기는
§9.7 에서 부속서 G 계수표와 값으로 대조돼 있으니, 그 위에 올라탄 대조다(I = 1·4·5, 프레임 1·125·128 바이트).

**시험 9 개**(`ShortenedCodeblockTests`, REQ-RS-05 신설 — 추적 24 → 25): 위 정의 대조 4 · CADU 길이 1 · 부호어당 16 개 정정(I = 1·4) 2 · 채움 자리 정정 실패 1 · 생성 조건 1.
기존 시험 102 개는 **손대지 않고 그대로 통과**했다(동기기 버퍼 상한 등이 CADU 길이를 코덱에서 받아 쓰기 때문이다). 뮤턴트 확인:
- Chien 탐색을 채움 자리까지 넓히기 → 채움 정정 시험이 실패(위의 `B4` → `77`).
- 신드롬 계산을 채움부터가 아니라 0 부터 → **동등**(111 개 통과). 앞쪽 0 은 Horner 계산에서 값을 0 으로 둔 채 지나가므로 건너뛰어도 같다 — 속도만 다르다.

### 9.9 표준 PN — 131071 비트 수열을 기본으로 (2026-09-23)

§9.6 에서 255 비트 수열을 표준 값과 맞췄지만, 그것은 **옛 시스템 호환용**(§10.4.2 "may")이었다. 표준의 기본은
131071 비트 수열이다(§10.4.1 "shall") — h(x) = x^17 + x^14 + 1, 코드블록마다 초기값 `11000111000111000` 에서 다시 시작한다(§10.4.3).
표준은 255 비트가 1/255 심볼율에 스펙트럼 선을 만들 수 있다고 경고한다. 이 수열이 없었다.

**또 방향 함정이었다.** 표준의 초기값 문자열을 왼쪽부터 첫 비트로 읽으면 수열이 `C7 1C 6E 46 EA …` 로 나오는데, 표준이 싣는 처음 40 비트는
`1C 71 B9 1B A9` 다. 그림의 레지스터가 X17…X1 순서로 적혀 있어 **문자열의 오른쪽 끝이 첫 비트**다. 점화식은 255 비트 때와 같은 꼴
s[n+17] = s[n+14] ⊕ s[n] 이다. 가능한 네 조합(초기값 방향 × 다항식/역다항식)을 Python 으로 다 돌려 40 비트와 맞는 것이 **하나뿐**임을 확인하고
주기가 131071 비트인 것도 확인한 뒤 옮겼다. PN 탭을 두 번 틀린 CH-1·CH-4 와 같은 종류의 함정이라 이번에는 값부터 확인했다.

**구현** — 코드블록마다 처음부터 다시 걸기 때문에 늘 같은 앞부분만 쓴다. 앞 16,383 바이트(주기 안쪽, 표준의 최대 코드블록 2,040 바이트보다 넉넉히 크다)를
표로 한 번 만들어 두고 XOR 만 한다. 초기값 상수는 표준의 문자열을 그대로 2진 상수로 옮겼고, 그 비트 0 이 첫 비트다.
`ChannelCodec` 의 기본을 131071 비트로 바꾸고 255 비트는 선택지로 남겼다 — 수열 종류는 물리 채널마다 미리 정하는 값이라 전송 데이터로 알리지 않는다(§10.1).

**시험 5 개**(REQ-PN-02 신설 — 추적 25 → 26): 표준의 40 비트 · 독립 구현(표준의 문자열을 그대로 들고 비트 배열 위의 점화식으로 돌린다 — 기준 자신도
40 비트로 먼저 확인)과 16,383 바이트 전량 · 자기 역원·255 바이트 주기 없음·길이 상한 · `ChannelCodec` 이 CADU 를 "RS 코드블록 ⊕ 고른 수열" 로 만드는지(두 수열).
기본값을 바꿨는데도 기존 시험 111 개는 손대지 않고 그대로 통과했다. 뮤턴트 확인: 초기값 방향을 뒤집으면 `C71C6E46EA`, 탭을 x^3 으로 바꾸면 `1C71FFFF00` 이
나와 두 대조 시험이 실패한다.

**처리량** — 표 조회로 체인이 **13 % 빨라졌다**(20,734 → 18,070 ns, §8.5). 할당은 그대로.

결과: 시험 116 통과 · 경고 0 · 라인 727/727 · 분기 304/304 · 추적 26/26. 뮤테이션 **94.97 %**(736 개, 새 PN 코드로 26 개 늘었다, [run 35829259218](https://github.com/Haejyn/ccsds-downlink-reliability/actions/runs/35829259218)) — 새 PN 코드(표 생성·131071 적용)에는 생존이 없고, 남은 생존은 이미 판정한 종류(메시지 문자열·동등한 throw 삭제·`>>>`)다.

### 9.10 외부 구현과의 대조 — libfec 와 바이트 단위로 (2026-09-23)

§9.7·§9.8 의 대조는 **표준 문서**(부속서 G 의 계수표, 가상 채움의 정의)와의 대조였다. 문서를 내가 읽고 옮긴 것이라, 같은 방향으로 잘못 읽었다면
양쪽이 함께 틀릴 수 있다(pdftotext 가 지수를 잘라 두 번 잘못 읽을 뻔했다). 그래서 **다른 사람이 쓴 코드의 실제 출력**과도 맞췄다 —
지상국 소프트웨어에서 널리 쓰이는 Phil Karn 의 libfec 가 가진 CCSDS RS 부호기·복호기(`encode_rs_ccsds` · `decode_rs_ccsds`)다.

**방법** — `tools/gen_golden_libfec.py` 가 libfec 를 고정 커밋(`9750ca0`)으로 받아 C 컴파일러로 빌드하고, 고정 시드로 만든 입력을 넣어 기준 벡터를 쓴다.
libfec 는 LGPL 이라 저장소에 넣지 않는다 — 하네스(`tools/libfec_vectors/vectors.c`, 이 저장소의 코드)와 벡터(데이터)만 넣었다.
CI 가 ubuntu 에서 벡터를 다시 만들어 저장소 파일과 대조한다(누가 벡터만 손으로 고치면 실패한다).

| 대조 | 규모 | 결과 |
|---|---|---|
| 부호화 | 가상 채움 Q = 0·1·95·100·222 × 입력 7 가지(무작위 3 · 모두 0 · 모두 FF · 첫/끝 심볼만 1) = 35 | **35/35 바이트 단위 일치** |
| 복호 | 가상 채움 5 가지 × 오류 0·1·8·16·17 = 25 | **25/25 판정 일치** — 정정 수·복호 결과까지 같고, 오류 17 개는 양쪽 모두 실패 |
| 채움 자리 정정 | 1 | **의도적으로 다르다** (아래) |

이 하나로 생성 다항식·이중 기저·**바이트 안의 비트 배치**·짧은 코드블록을 한 번에 확인했다. libfec 의 생성 다항식 표도 부속서 G 와 같은 지수
(`0, 249, 59, 66, …`)를 쓰고, 이중 기저 변환의 행도 `8d ef ec 86 fa 99 af 7b` 로 같다 — 세 출처(표준 문서 · libfec · 이 구현)가 같은 값을 가리킨다.

**libfec 에도 채움 자리 약점이 있었다.** libfec 의 `decode_rs.h` 는 오류 위치가 채움 자리(`loc < pad`)로 나오면 **그 정정만 건너뛰고 정정 수를 그대로 돌려준다** —
실패로 알리지 않는다. §9.8 의 수신어(채움 자리와 거리 1 인 부호어로 가는 것)를 넣으면 libfec 는 "정정 1 개, 성공" 이라며 **첫 바이트가 바뀐 데이터를 내보낸다.**
이 구현은 같은 입력을 실패로 알린다(REQ-RS-05). 널리 쓰이는 참조 구현도 이 자리를 막지 않는다는 것이라, 차이를 시험으로 고정했다
(`On_a_correction_that_lands_in_the_fill_libfec_passes_damaged_data_and_this_decoder_refuses`).

**시험 3 개**(REQ-RS-06 신설 — 추적 26 → 27). 뮤턴트: 이중 기저 변환의 행 하나를 비트 순서만 뒤집어도 부호화·복호 대조가 모두 실패한다.

**아직 못 한 것** — 실제 위성에서 캡처한 비트열과의 대조. libfec 와 같다는 것은 "널리 쓰이는 관례와 같다" 이지 "실제 링크에서 확인했다" 가 아니다. → **§9.11 에서 했다.**

결과: 시험 119 통과 · 경고 0 · 라인 727/727 · 분기 304/304 · 추적 27/27.

### 9.11 실제 위성의 비트 — Astrocast 0.1 녹음을 프레임 CRC 까지 (2026-09-23)

| ASM 동기 | CADU 3 장 — 마커 비트 오류 0 (기본 설정 `FrameSynchronizer`, CADU 사이에 프리앰블이 끼어 있어 장마다 다시 잡는다) |
| PN 되돌림 · RS 복호 | 3 장 × 5 레인 **전부 성공, 정정 0** — libfec 도 같은 입력에서 15/15 성공 |
| 전송 프레임 | **송신기가 계산한 CRC-16 이 맞는다** · SCID 1 · VC 4 · 마스터 프레임 카운트 0x17 → 0x18 → 0x19 · 제1 헤더 포인터 0x7FE(유휴 데이터) · OCF 있음 |
| 판별력 | PN 을 131071 비트로 바꾸면 3 장 모두 RS 실패 |
| 정정 경로 | 실제 코드블록에 레인마다 심볼 오류 16 개 → 원래 프레임 복원(정정 80), 17 개 → 실패 |

RS 는 부호어가 맞는지만 안다. **프레임 CRC 는 송신기가 따로 계산한 값**이라, 이것까지 맞으면 인터리빙을 푸는 방향과 되살린 바이트의 순서까지
송신기와 같다는 뜻이다. 이중 기저의 비트 배치(§4.3.9.2, MSB = z0)도 여기서 확인됐다 — §9.7 의 "구현의 선택" 이 실제 송신기와 같다.

**처음엔 전부 실패했다 — 원인은 복조기였다.** 공칭 9600 baud 에 Gardner 타이밍 복원을 걸어 복조하니 ASM 은 오류 0~1 비트로 잡히는데
RS 는 15 레인 모두 실패했다. PN·기저·인터리빙 조합을 다 바꿔도, libfec 로 돌려도 실패였다. 같은 내용의 유휴 프레임 두 장을 비교하니
차이가 대부분 **1 비트짜리이고 프레임 뒤로 갈수록 촘촘했다** — 시계가 밀리는 모양이다. 영점 교차 시각이 한 격자에 얼마나 모이는지(원형 평균의 크기)를
주기별로 재 보니, 9600 baud(5.000 샘플)에서는 0.02, **9677 baud(4.960 샘플)에서 0.93** 이었다. 이 녹음의 심볼 속도는 공칭보다 0.8 % 빠르다
(위성의 발진기인지 녹음 장비의 표본화율인지는 이 자료로 가릴 수 없다). ASM 32 비트는 짧아 밀림이 드러나지 않았고, 10,200 비트짜리 코드블록에서만 드러났다.
주기를 실측값으로 고정하자 3 장이 오류 없이 풀렸다. **동기 마커가 잡힌다는 것은 복조가 맞다는 증거가 아니었다.**

**시험 3 개**(REQ-CAP-01 신설 — 추적 27 → 28). 한계: 녹음이 하나이고 짧아(3 장) 신호가 깨끗하다 — 실제 링크의 오류 상황은 위의 주입으로만 본다.
유휴 프레임이라 패킷 계층(추출기)까지는 가지 않는다.

결과: 시험 122 통과 · 경고 0 · 라인·분기 100 % · 추적 28/28.

### 9.12 인터리빙 깊이 — 표준이 허용하는 여섯 값만 (2026-09-23)

§4.3.5.1 은 인터리빙 깊이를 **I = 1, 2, 3, 4, 5, 8** 로 못 박는다. 이 구현은 `I ≥ 1` 이면 무엇이든 받았다 — 산술은 I = 6 이든 16 이든 돌아가서
시험이 한 번도 걸리지 않았지만, 그렇게 만든 코드블록(예: I = 6 이면 1,530 바이트)은 어떤 표준 수신기와도 맞출 수 없다.
`ReedSolomonCodec.AllowedInterleavingDepths` 를 공개 목록으로 두고 두 생성자가 같은 검사를 쓴다(`ChannelCodec` 이 먼저 부른다 — 용량 계산 전에).

**시험** — 거부: −1·0·6·7·9·16(사이에 낀 값·8 을 넘는 값) × 두 생성자, 예외에 거부한 값이 실린다. 허용: 여섯 값 전부 받고 코드블록 255·I.
기존 왕복 시험을 1·4·5 → 여섯 값 전부로, 버스트 시험을 4·5 → 2·4·5·8 로 넓혔다. REQ-RS-07 신설 — 추적 28 → 29.

결과: 시험 122 → 132 · 경고 0 · 라인 732/732 · 분기 306/306 · 추적 29/29.

## 10. 뮤테이션을 심판으로 세운 시험 생성 루프 (2026-09-16)

§4 에서 사람이 손으로 한 일 — 생존 뮤턴트를 읽고, 분류하고, 죽일 시험을 쓰고, 다시 재서 확인한 것 — 을
그대로 자동화했다. 도구는 `tools/mutation_loop/`, 심판은 **생성 전후의 생존 뮤턴트 수**다.

```
생존 목록(축약) → 프롬프트 → 시험 초안 → 컴파일·실행 → 대상 파일만 뮤테이션 재측정
                                                      ↓
                                      생존이 줄면 채택, 아니면 폐기 (판정은 숫자가 한다)
```

**왜 심판을 따로 두나** — 시험을 생성하는 것 자체는 쉽다. 어려운 것은 그 시험이 쓸모 있는지 판정하는 일이다.
"보기에 괜찮다" 로 받으면 시험 수만 늘고 결함 검출력은 그대로다. 그래서 **이미 있는 지표**에 판정을 맡겼다.

### 10.1 결과 — 생존 10 → 7 (`ReedSolomon.cs`)

| | 넣기 전 | 넣은 뒤 |
|---|---|---|
| 대상 파일 생존 | 10 | **7** |
| 점수 (대상 파일만) | — | **95.60 %** (죽임 146 · 타임아웃 6 · 생존 7) |

**전체로 보면 93.27 % → 93.41 %** ([run 35082702568](https://github.com/Haejyn/ccsds-downlink-reliability/actions/runs/35082702568), 세 잡 성공 · 커버리지 100 % · 추적 23/23).
대상 파일에서 3 개가 죽었는데 전체 생존은 46 → 45 로 **1 개만 줄었다.** 숫자를 그대로 적으면:

| | 채널 부호 추가 뒤 | RS 실패 경로 시험 추가 뒤 |
|---|---|---|
| 죽임 · 타임아웃 | 579 · 58 | **574 · 64** |
| 생존 | 46 | **45** |
| 채점 대상 | 683 | 683 |

죽임이 5 줄고 타임아웃이 6 늘었다 — **죽던 변이 일부가 타임아웃으로 분류가 바뀐 것**이다(둘 다 "죽은 것" 으로 세므로 점수는 오른다).

**점수는 소수점까지 인용하면 안 된다.** 그다음 푸시는 **코드를 한 줄도 바꾸지 않았는데**(문서와 CI 워크플로만) 93.41 % → **93.70 %** 로 움직였다
([run 35085937216](https://github.com/Haejyn/ccsds-downlink-reliability/actions/runs/35085937216): 죽임 579 · 생존 43 · 타임아웃 61).
타임아웃 경계에 걸친 변이가 실행마다 죽음/생존을 오가기 때문이다. 이 저장소에서 뮤테이션 점수는 **93 % 대**라고 읽고,
비교는 **같은 실행 안에서 생존 목록을 보고** 한다.
새 시험이 RS 복호를 무거운 입력으로 여러 번 돌리기 때문에, 그 변이들이 시간 안에 못 끝난 것으로 보인다.
**로컬에서 대상 파일만 잰 3 개 감소와 전체 1 개 감소는 이렇게 어긋난다** — 부분 측정과 전체 측정을 같은 자로 보면 안 된다는 뜻이다.

죽은 셋은 전부 **REQ-RS-03 의 핵심**이었다.

| 죽은 변이 | 무엇을 지키게 됐나 |
|---|---|
| `errorCount == 0 \|\| errorCount > CorrectableSymbols` → `&&` | 정정 능력 초과 판정 |
| 그 분기의 `return false` → `true` | **실패 선언 자체** |
| `ParitySymbolsPerCodeword + 1` → `- 1` | Berlekamp-Massey 작업 공간 크기 |

생성된 시험은 무작위로는 사실상 나오지 않는 오류 패턴을 **체 이론으로 직접 구성**했다 —
15 칸 간격 오류 17 개로 S17 만 남겨 근이 17 개인 Λ 를 만들고, `Π(x − α^j)` 로 S1…S30 을 지워 BM 길이를 31 로 밀어 올린다.
사람이 검토해 [`ReedSolomonFailurePathTests`](../tests/SpaceLink.Tests/ReedSolomonFailurePathTests.cs) 로 남겼다.

### 10.2 프롬프트 세 판 — 무엇을 금지하느냐가 갈랐다

`bare`(변이 줄만) · `context`(주변 코드 + 기존 시험 이름) · `guarded`(+ "먼저 (a) 동등 / (b) 문구 / (c) 진짜 구멍 으로 나누라").
세 판 모두 **메시지 문구 단언 금지**와 **구현 세부 단언 금지**를 넣었다 (§4 의 원칙).

`guarded` 를 생존 뮤턴트가 전부 "동등·문구" 인 `PacketExtractor.cs` 에 돌렸더니 **시험을 한 줄도 쓰지 않았다.**
억지로 점수를 올리지 않는 것이 이 루프의 요구사항이므로, 그것이 정답이다.
같은 판을 진짜 구멍이 있는 `ReedSolomon.cs` 에 돌렸을 때만 시험을 썼다.

### 10.3 실패한 여섯 번은 전부 하네스 쪽이었다

모델이 잘못 판단한 적은 없었다. 막힌 것은 매번 도구를 부르는 쪽이었고, 그 기록을 남긴다.

| # | 증상 | 원인 |
|---|---|---|
| 1 | 세 판 모두 "응답 없음" | `claude -p` 를 stdin 을 닫지 않고 호출 — 3 초 기다렸다 경고만 남기고 끝난다 |
| 2 | 생성 직후 `FileNotFoundError` | Windows `subprocess` 는 `env["PATH"]` 를 바꿔도 **부모 PATH** 로 실행 파일을 찾는다 → 전체 경로로 호출 |
| 3 | 실패한 초안이 저장소에 남음 | 예외 경로에 정리가 없었다 → `finally` 로 되돌린다 |
| 4 | `NameError`·`TypeError` | 리팩터 중 인자를 빠뜨렸다 |
| 5 | "컴파일 실패" 만 남고 이유가 없음 | **실패를 판정만 하고 배우지 못했다** — 초안과 오류 줄을 `build/loop-drafts/` 에 보관하도록 고쳤다 |
| 6 | `No .csproj found` → `Failed to identify target frameworks` | Stryker 를 저장소 루트에서 돌렸고, 그다음엔 Stryker 가 **Visual Studio BuildTools 의 MSBuild(.NET Framework 판)** 를 골라 `net10.0` 을 해석하지 못했다. 시험 프로젝트 폴더에서 돌리고 `MSBuildSDKsPath`·`MSBUILD_EXE_PATH` 를 SDK 쪽으로 못 박아 해결 (CI(ubuntu) 에서 같은 명령이 도는 이유 — 거기엔 VS BuildTools 가 없다) |

5 번이 가장 나빴다. 실패를 **판정하는** 장치는 있는데 **왜 실패했는지 배우는** 장치가 없으면 루프는 돌지 않는다.

### 10.4 한계

- **CI 에서 돌리지 않는다.** 모델을 반복 호출하므로 사람이 명시적으로 실행할 때만 돈다.
- **생성한 시험을 그대로 커밋하지 않는다.** 채택은 루프의 판정일 뿐이고, 남길지는 사람이 읽고 정한다.
  실제로 앞선 초안에는 `Assert.Equal(48, divisors)` 처럼 **구현이 아니라 시험 자신의 열거 논리**를 검증하는 줄이 있었고, 그런 단언은 걷어냈다.
- **한 바퀴가 11 분**이다 (모델 호출 ~6 분 + 측정 ~5 분). 빠른 되먹임 고리는 아니다.
- 표본이 작다 — 대상 파일 둘, 프롬프트 세 판, 채택 한 번. "효과가 있다" 가 아니라 **"이 조건에서 이렇게 나왔다"** 로 읽어야 한다.
