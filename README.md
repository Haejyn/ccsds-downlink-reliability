# ccsds-downlink-reliability — SpaceLink

지상국 영상수신처리의 첫 단계인 **CCSDS TM 다운링크 수신 처리기**(C# / .NET 10)와 그 신뢰성 시험.
위성이 보낸 전송 프레임(CCSDS 132.0-B)을 검증하고, 가상 채널별로 Space Packet(CCSDS 133.0-B)을 재조립하며, 링크 이상을 이벤트로 보고한다.

**핵심 계약: 손상됐을 가능성이 있는 패킷은 절대 내보내지 않고, 손상과 무관한 패킷은 모두 복구한다.**
요구사항과 판정 기준: [`docs/requirements.md`](docs/requirements.md)

```
dotnet test tests/SpaceLink.Tests -c Release -p:CollectCoverage=true
```

## 발견한 결함 C-1

**증상** — 256 장 단위로 프레임이 연속 유실되면 8 비트 가상 채널 프레임 카운트가 한 바퀴 돌아 유실이 보이지 않는다. 이때 조립 중이던 패킷에 전혀 다른 패킷의 뒷부분이 이어 붙어, **첫 설계는 원본에 없는 손상 패킷을 내보냈다** (시험 5건 실패).

**원인** — 프레임 CRC·프레임 카운트·제1 헤더 포인터는 모두 *프레임 단위* 정보다. 우연히 경계가 맞으면 프레임 계층만으로는 잘못 이어 붙인 패킷을 원리적으로 구분할 수 없다.

**조치** — 패킷 오류 제어(PEC, 패킷 끝 CRC-16)를 선택 기능으로 넣고, 수신 쪽이 검증해 불일치하면 버리고 다음 제1 헤더 포인터에서 다시 동기화한다. 비용은 패킷당 2 바이트.

**고정한 시험** — (1) PEC 없이는 손상 패킷이 실제로 나온다(결함이 조건에서 재현됨을 고정) (2) PEC 를 켜면 같은 조건 5 시드 × 40 시도에서 손상 패킷 0 (3) PEC 는 패킷 단일 비트 오류 전수를 잡는다.

## 한계와 다음

- **처리량 수치를 시험 안에서 재지 않는다** — 예전 README 의 "약 3만 프레임/초" 는 xUnit 이 시험을 병렬로 돌리는 동안 잰 값이라 수신기 성능이 아니라 CPU 경합을 재고 있었다. 단독 측정은 20~25배 빠르다. 지금 수치는 전부 `benchmarks/SpaceLink.Benchmarks` (단일 스레드) 에서 나온다
- **2.85 Gbps 는 추출 단계만의 값이다** — 지상국이 실제로 지나는 채널 체인(ASM 동기·PN·RS 복호까지)은 약 27,000 프레임/초로 **추출 단계의 1/95** 다. 시간의 99 % 가 앞 세 단계에 든다. 예전 문서는 이 구분 없이 "수신기 2.85 Gbps" 로 읽힐 수 있었다 ([시험 보고서 §8.5](docs/test-report.md))
- **남은 할당** — 프레임당 244 B 의 대부분은 `SpacePacket` 이 패킷마다 자기 데이터 배열을 갖기 때문이다. 더 줄이려면 호출자가 버퍼를 넘기거나 풀을 쓰는 형태로 **공개 API 를 바꿔야 한다** — 지금은 쉬운 API 를 택했다
- **RS 는 이제 CCSDS 의 코드다** — 생성 다항식의 근을 표준(§4.3.4, `(α^11)^j, j = 112…143`)대로 고치고 이중 기저(dual basis, §4.3.9, 부속서 F) 변환을 넣었다. 부속서 G 가 싣는 생성 다항식 계수 32 개와 값으로 대조한다 ([시험 보고서 §9.7](docs/test-report.md)). PN 수열도 표준이 싣는 처음 40 비트와 대조했다 — 다만 표준의 기본인 131071 비트 수열은 없고 옛 시스템 호환용 255 비트만 있고, 비트 전송 순서(§4.3.9.2)는 실제 캡처와 대조하지 못했다
- 컨볼루션·터보·LDPC 부호, AOS 프레임, 패킷 부헤더(시각 코드)는 범위 밖
- 이벤트·예외의 **메시지 문구는 계약이 아니라고 보고 시험하지 않는다** — 생존 뮤턴트 대부분이 이 문자열이라, 문구를 계약으로 삼지 않는 한 점수에 상한이 있다 ([시험 보고서 §4](docs/test-report.md))
